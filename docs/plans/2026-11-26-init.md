# kuri 초기 구현 계획

## 목표와 현재 상태

macOS에서 `127.0.0.1:80`과 `[::1]:80`으로 HTTP 요청을 받고, 호스트 이름으로 Kubernetes Service를 선택해 포트포워딩합니다. 사용자는 `go run .`과 빌드한 바이너리로 실행, 종료, 상태 확인을 할 수 있습니다.

저장소에는 [초기 요구서](../reqs/2026-11-26-init.md)와 Go 모듈 선언만 있습니다. 모듈은 `github.com/crmin/kuri`이며 로컬 Go 버전은 `go1.27.3 darwin/arm64`입니다.

## 승인할 동작

| 항목 | 계획에 반영한 동작 |
| --- | --- |
| 포워딩 만료 | 새 연결이 준비되면 60분을 부여합니다. 같은 포워딩을 쓰는 다음 요청부터 마지막 요청 시각 기준 60초로 초기화합니다. 15초마다 요청하면 연결을 유지합니다. 10초 점검과 복구는 만료 시각을 연장하지 않습니다. |
| launchd의 실행 파일 | launchd 경로에서는 `go run .`이나 다른 빌드의 CLI를 호출해도 서버는 등록한 바이너리로 실행됩니다. IPC 규약이 호환되지 않으면 요청을 중단하고 영어로 갱신 방법을 안내합니다. 최신 서버 소스를 적용하려면 설치 바이너리를 갱신합니다. |
| launchd에서 `stop` | 현재 백그라운드 프로세스를 종료합니다. 소켓 등록은 유지하므로 후속 연결로 새 PID가 시작될 수 있습니다. 재활성화를 막으려면 관리자가 소켓 등록을 해제합니다. |
| 호스트와 로그 식별자 | Type B의 `port`는 숫자 Service 포트입니다. `config_id`는 실제 context, namespace, service, Service 포트로 만든 안정적인 문자열입니다. `alias`는 정규화한 요청 호스트입니다. 로그의 `remote_port`와 표의 `remote port`는 Service 포트입니다. |
| DNS에 넣기 어려운 context 이름 | 소문자 DNS 레이블인 context 이름을 그대로 사용합니다. 그 외에는 원래 이름의 SHA-256 앞 16자리 16진수에 `ctx-`를 붙입니다. 충돌한 별칭의 A/B 요청은 오류로 처리합니다. help에서 별칭 규칙을 안내하고 README에 계산 예시를 둡니다. 로그와 `state`는 kubeconfig의 원래 이름을 표시합니다. |
| 적용 범위 | Kubernetes TCP Service 뒤의 평문 HTTP를 프록시합니다. selector가 없거나 포워딩 가능한 Pod가 없는 Service, UDP/SCTP 포트는 연결 실패로 처리합니다. |

## 실행 흐름

1. 서버를 시작할 때 `$HOME/.kube/config`에서 context와 `current-context`를 읽습니다. 개별 클러스터 접속은 해당 context의 요청이 들어올 때 시작합니다. 일반 실행과 LaunchDaemon은 같은 사용자 홈을 사용합니다. kubeconfig 변경은 재시작하면 반영합니다.
2. 요청 `Host`에서 `:80`, 대소문자, 마지막 점을 정규화하고 세 가지 형식만 허용합니다. 새 경로를 해석할 때 A와 C는 Service 포트가 하나면 그 포트, 여러 개면 이름이 `http`인 포트를 선택합니다. B는 요청한 숫자가 `Service.spec.ports[].port`와 일치해야 합니다. C는 설정의 `current-context`를 씁니다.

   | 형식 | 호스트 |
   | --- | --- |
   | A | `{service}.{namespace}.{ctx}.kuri.localhost` |
   | B | `{port}.{service}.{namespace}.{ctx}.kuri.localhost` |
   | C | `{service}.{namespace}.kuri.localhost` |

3. 먼저 이전에 해석한 경로에서 준비된 포워딩을 찾습니다. 연결 키는 context, namespace, service, Service 포트입니다. 명시 포트는 키로 직접 조회하며 A와 C의 기본 포트는 context까지 해석한 뒤 같은 매핑을 사용합니다. 준비된 포워딩은 Kubernetes API 조회 없이 재사용합니다. 준비 중인 연결은 같은 키의 동시 요청이 공유합니다. 최초 연결과 복구에서 Service를 조회하고 selector로 실행 가능한 Pod를 선택합니다. Kubernetes가 정한 숫자 포트, 이름 포트, headless Service의 `targetPort` 해석을 적용해 `pods/portforward`를 엽니다. Service 포트가 바뀌면 복구 또는 다음 최초 연결에서 경로 매핑을 갱신합니다.
4. `[30000, 40000)`에서 무작위 순서로 아직 점유되지 않은 포트를 확인합니다. 외부 점유 후보는 로컬에서 걸러내고 실제 포워더가 루프백 바인딩을 마친 뒤 준비 처리합니다. 확인과 실제 바인딩 사이에 생긴 포트 충돌은 다른 후보로 재시도합니다. 전체 풀이 찼으면 가장 오래 연결된 자체 포워딩을 종료하고 포트가 풀린 뒤 같은 포트를 씁니다. 전부 다른 프로세스 소유라면 포트 부족을 반환합니다.
5. 10초마다 새 연결을 통해 제한시간이 있는 `HEAD /` 요청을 보냅니다. 리다이렉트는 따라가지 않으며 유효한 HTTP 응답은 상태 코드와 관계없이 연결 성공으로 봅니다. 포워더 종료 신호 또는 전송 오류가 나면 만료 전에 복구합니다. 준비된 대체 Pod가 있으면 실패한 Pod보다 먼저 시도합니다. 복구한 터널에서 실제 HTTP 응답을 확인한 뒤 요청을 연결합니다. 복구에 실패하면 만료까지 제한된 간격으로 재시도합니다. 점검은 접근 로그와 만료 갱신 대상에서 제외합니다.
6. Go `httputil.ReverseProxy`로 요청의 경로, 쿼리, 메서드, 본문과 Host를 전달합니다. 요청은 준비된 포워딩의 실행 번호와 전용 HTTP transport를 받습니다. 관리자는 포워딩을 만료, 교체 또는 회수할 때 그 transport의 새 연결을 막고 진행 중인 연결 시도를 끝낸 뒤 포트를 풀어 줍니다. 대기하던 이전 요청과 지연된 종료 콜백은 해당 실행 번호에만 영향을 줍니다.
7. 서버가 받은 모든 사용자 요청에 대해 시각, 도메인, 연결 결과를 영어 JSON Lines로 기록합니다. upstream 응답을 받으면 HTTP 상태와 별개로 연결 성공을 기록합니다. 성공 필드는 `config_id`, `alias`, `context`, `local_addr`, `local_port`, `namespace`, `protocol`, `remote_port`, `service`입니다. 실패에는 영어 원인을 남깁니다. 토큰이나 요청 본문은 로그에 기록하지 않습니다.
8. 단일 writer가 `$HOME/.kuri/access.log`를 관리합니다. 로그를 추가하기 전에 72시간보다 오래된 줄을 제거합니다. 새 줄을 더하면 100MiB를 넘는 경우 한도에 맞을 때까지 오래된 줄부터 더 제거합니다. 정리가 필요한 경우 기존 줄과 새 줄의 순서를 유지해 같은 디렉터리의 임시 파일에 쓴 뒤 교체합니다. 정리가 필요 없는 경우 뒤에 추가합니다. 정지 중에는 정리하지 않습니다. 서버 준비와 `stop`에 PID를 기록합니다.

## macOS 실행과 상태 확인

| 명령 | 실행 결과 |
| --- | --- |
| `go run .` | 포그라운드에서 두 루프백 리스너를 직접 엽니다. 서버 로그를 콘솔과 파일에 보냅니다. 권한 오류나 등록된 소켓 점유가 확인되면 LaunchDaemon 제어 소켓으로 포그라운드 시작을 요청하고 로그를 콘솔로 중계합니다. `Ctrl+C`는 시작을 승인받은 인스턴스만 정상 종료합니다. 기존 서버에 대한 중복 실행은 오류로 처리합니다. |
| `go run . help` | 실행 모드와 `help`, `start`, `stop`, `state` 도움말을 영어로 한 번 출력합니다. |
| `go run . start` | 직접 바인딩할 수 있으면 터미널과 분리된 백그라운드 자식으로 실행합니다. 등록된 LaunchDaemon을 사용할 때는 사용자 전용 소켓으로 백그라운드 시작을 요청하고 준비 완료 PID를 받습니다. 서버가 파일에 해당 PID로 시작을 기록한 뒤 성공을 반환합니다. 이를 통해 GUI 앱 없이도 터미널을 닫을 수 있습니다. |
| `go run . stop` | 실행 중인 백그라운드 인스턴스에 종료를 요청하고 실제 프로세스가 끝난 것을 확인한 뒤 종료한 PID를 표준 출력에 표시합니다. 백그라운드 인스턴스가 없으면 영어 오류를 표준 출력에 쓰고 종료 코드 1을 반환합니다. `go run` 자체는 실패 시 stderr에 종료 상태를 덧붙일 수 있습니다. |
| `go run . state` | 표준 출력에 실행 상태를 표시합니다. 실행 중이면 PID, 시작 시각, 현재 연결 수와 Bubble Tea 인라인 표를 표시합니다. 상태를 조회해도 LaunchDaemon이 시작되거나 접근 로그가 추가되지 않습니다. |

- 시스템 LaunchDaemon을 최초 등록할 때 관리자 권한을 사용합니다. plist에는 `UserName`, 명시적인 사용자 `HOME`, 영구 경로에 설치한 바이너리, IPv4/IPv6 루프백 소켓과 활성화용 Unix 소켓을 설정합니다. Unix 소켓은 관리자 소유 디렉터리에 만들고 `SockPathOwner`와 `SockPathMode`로 지정 사용자만 접근하게 합니다. `RunAtLoad`와 `KeepAlive`의 기본값은 끕니다. 일반 CLI는 시스템 도메인을 수정하지 않고 소켓으로 활성화를 요청합니다.
- Darwin cgo 브리지는 `launch_activate_socket()`을 호출해 `HTTP` 항목의 두 FD와 `Control` 항목의 Unix FD를 Go 리스너로 변환합니다. 변환 중 하나라도 실패하면 이미 연 FD와 리스너를 닫습니다. 등록 전 권한 부족과 다른 프로그램의 포트 사용은 서로 다른 영어 오류로 표시합니다.
- 첫 HTTP 연결과 인증된 CLI 시작 요청 중 먼저 시작 권한을 확보한 쪽이 인스턴스 모드를 한 번 정합니다. HTTP 연결은 백그라운드 모드로 시작합니다. CLI는 포그라운드 또는 백그라운드 모드를 명시하고 실행별 토큰, 준비 완료 PID를 받습니다. 포그라운드 소유자에게 초기 시작 로그부터 보냅니다.
- `state`와 `stop`은 서버가 실행 중일 때만 열리는 `$HOME/.kuri`의 사용자 전용 Unix 소켓을 사용합니다. 프로세스 잠금으로 사용자당 한 인스턴스를 유지합니다. `stop`은 인증된 IPC로 확인한 PID의 종료 알림을 구독한 다음 정리를 요청합니다. 서버는 HTTP 리스너를 닫고 처리 중인 요청을 기다립니다. 종료 시한을 넘긴 요청은 취소하고 실패로 기록합니다. 각 요청의 접근 로그를 한 번씩 기록한 뒤 PID가 담긴 종료 로그를 추가합니다. CLI는 해당 프로세스가 끝난 뒤 PID를 출력합니다. 바로 재시작하는 경우 launchd의 기동 제한을 포함하는 대기 기한을 사용합니다.
- README에 설치 바이너리의 고정 경로, `CGO_ENABLED=1` 빌드, 관리자 등록과 해제, 바이너리 갱신 순서를 적습니다. 호환되지 않는 CLI/서버 조합의 제어 요청은 실행 전에 거절합니다.
- 상태 표의 헤더는 `ctx`, `namespace`, `service`, `remote port`, `local port`, `connected`입니다. Service 포트에 이름이 있으면 `8080 (http)` 형식으로 표시합니다. 120초 미만, 60분 미만, 24시간 미만, 그 이후 순으로 초, 분, 시간, 일을 고르고 해당 단위에서 반올림합니다. 연결 수와 행은 같은 스냅샷에서 만듭니다. 재연결에 성공한 경우 현재 터널이 준비된 시각부터 표시합니다.

| 순서와 커밋 메시지 | 파일과 변경 위치 | 먼저 작성할 검증과 커밋 시점 |

## 검증과 운영 조건

- `go test ./...`, `go test -race ./...`, `go vet ./...`, `go build .`을 실행합니다. 실제 Kubernetes 없이 검증할 수 있는 테스트는 임시 HOME, 가짜 시계, HTTP 테스트 서버와 가짜 포워더를 사용합니다.
- 로컬 테스트 클러스터에서 Type A/B/C, Service 포트와 `targetPort`가 다른 경우, 이름 포트와 Pod 교체, 오류 로그, 같은 연결의 재사용을 확인합니다. `curl --resolve`로 IPv4/IPv6 요청을 각각 확인하고 일반 브라우저에서 `*.kuri.localhost`의 주소 해석도 확인합니다.
- macOS에서 별도 테스트 계정 또는 테스트 HOME을 사용해 `plutil -lint` 후 LaunchDaemon 수동 등록, 기본 미실행 상태, 첫 요청 활성화, 일반 사용자 PID, `start`와 `stop` 직후 로그, 다음 연결의 재활성화를 확인합니다. `stop` 직후 `state`와 `start`를 순서대로 실행해 이전 PID 종료와 새 PID 준비를 검사합니다. 빌드한 바이너리와 `go run .` 양쪽에서 확인하며 테스트 등록은 마친 뒤 해제합니다.
- LaunchDaemon을 등록한 상태에서 서버가 꺼져 있으면 일반 사용자로 `go run .`을 실행합니다. 첫 시작 로그가 콘솔과 파일에 기록되고 `Ctrl+C`가 그 PID를 종료하는지 확인합니다. HTTP 요청으로 백그라운드 서버를 먼저 띄운 경우에는 `go run .`의 중복 실행 오류를 확인하고 `state`에서 같은 PID가 실행 중인지 검사합니다.
- kubeconfig 사용자의 Service GET, Pod 조회 및 `pods/portforward` 권한이 필요합니다. exec 인증 플러그인이 필요한 환경에서는 LaunchDaemon의 명시적 PATH와 비대화식 인증을 확인합니다. 포트 80 점유, DNS 해석, Kubernetes 인증 상태는 실제 환경에서 별도로 확인해야 합니다.
- 백엔드가 HEAD 요청에 유효한 HTTP 응답을 하지 않으면 점검이 연결 오류로 처리됩니다. 100MiB에 가까워진 접근 로그에서는 새 요청마다 파일 대부분을 다시 쓸 수 있습니다. 한도에 도달한 상태에서 연속 요청을 보내고 응답 지연과 로그 보존을 확인합니다. 관리자 권한이 필요한 검증은 자동 테스트 결과와 함께 기록합니다.

## 근거

- LaunchDaemon과 소켓 활성화는 Apple 문서 및 로컬 `man launchd.plist`, `man launchctl`을 따릅니다. macOS 소스에서 IPv4와 IPv6의 특정 주소에 대한 낮은 포트 권한 확인을 확인했습니다. [Creating Launch Daemons and Agents](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html), [launch_activate_socket](https://developer.apple.com/documentation/xpc/launch_activate_socket), [XNU IPv4](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/netinet/in_pcb.c), [XNU IPv6](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/netinet6/in6_pcb.c)
- Service 포트는 선택된 Pod의 대상 포트에 매핑됩니다. Pod가 종료되면 세션이 끊길 수 있으며 selector가 없는 Service는 `kubectl port-forward`가 지원하지 않습니다. [kubectl port-forward](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_port-forward/), [Kubernetes Service](https://kubernetes.io/docs/concepts/services-networking/service/)
- 상태 표의 터미널 렌더링은 Bubble Tea와 Bubbles table을 사용합니다. [Bubble Tea 예제](https://github.com/charmbracelet/bubbletea/tree/main/examples#table)
