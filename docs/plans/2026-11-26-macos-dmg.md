# macOS용 kuri 앱과 DMG 패키징 계획

## 목표와 완료 기준

사용자가 `kuri.dmg`를 더블클릭하면 Finder에 밝은 배경, 왼쪽의 kuri 앱, 가운데의 오른쪽 화살표, 오른쪽의 Applications 바로가기가 보입니다. 앱을 바로가기 위에 놓으면 `/Applications/kuri.app`으로 복사됩니다. 복사한 앱을 더블클릭하면 터미널 창 없이 번들 안의 `kuri start`를 한 번 실행합니다.

산출물은 로컬 `dist/kuri.dmg`, 빌드 스크립트, 테스트, 사용 안내와 로컬 Git 커밋입니다. 사용자 지정 범위에 따라 원격 push, PR, 릴리스 업로드, 배포는 제외합니다. 앱 실행 중 `kuri install`을 호출하지 않습니다. Developer ID 서명, 공증, 티켓 첨부도 생략합니다.

## 현재 동작과 호환성

- `main.go`의 `run`은 인자가 없으면 포그라운드로 실행합니다. `start`는 백그라운드 시작을, `install`은 시스템 시작 프로그램 등록을 담당합니다. Finder용 런처를 별도로 두면 기존 CLI와 내부 명령을 그대로 사용할 수 있습니다.
- `internal/daemon/app.go`의 `App.run`은 기존 서버 PID와 활성화 소켓을 먼저 확인합니다. 이미 실행 중이면 중복 기동을 막습니다. 80번 포트 접근 권한이 부족하면 `internal/launchd/install_darwin.go`의 `Register`가 관리자 인증을 요청할 수 있습니다. 최초 등록은 서버 실행 파일을 시스템 경로에 복사하고 요청 시 실행하는 LaunchDaemon을 등록합니다. 기존 등록을 재사용하므로 앱 교체만으로 이미 등록된 서버 복사본이 갱신된다고 안내하지 않습니다. 근거는 `deploy/launchd/install.sh`, plist와 `docs/reqs/2026-11-26-init.md`입니다.
- 현재 README는 소스 빌드부터 설명합니다. 서버는 해당 계정의 `~/.kube/config`를 읽습니다. 인증 플러그인이 필요하면 터미널 입력 없이 실행할 수 있어야 합니다. Finder에서 시작한 프로세스는 셸의 초기화 파일을 읽지 않으므로 런처는 기존 PATH에 누락된 Homebrew 표준 경로를 추가합니다. 경로는 `deploy/launchd/com.github.crmin.kuri.plist`를 기준으로 삼습니다.
- 사전 평가에서 Apple Silicon과 Intel용 Go CLI 빌드, Universal 바이너리 생성, Apple Silicon에서 `kuri help` 실행을 확인했습니다. 앱 번들, Finder 화면과 실제 드래그 설치는 구현 후 검증합니다.

## 1. Finder에서 실행할 앱

1. `cmd/kuri-launcher/main_darwin.go`에 작은 Go 런처를 추가합니다. 자신의 실행 파일 위치에서 같은 디렉터리의 `kuri`를 찾고 그 절대 경로를 `syscall.Exec`로 실행합니다. 인자는 `start` 하나로 고정합니다. Finder가 전달한 인자, 현재 디렉터리, 시스템에 설치된 동명의 CLI는 실행 대상을 바꾸지 않습니다. launchd 전용 `KURI_LAUNCHD_START` 값은 자식 환경에서 제거해 일반 사용자의 시작 경로를 택합니다.
2. `deploy/macos/Info.plist`에 번들 유형 `APPL`, 고유 식별자, 표시 이름 `kuri`, 실행 파일 `kuri-launcher`, 앱 아이콘과 `LSUIElement`를 설정합니다. `deploy/macos/kuri.icns`는 kuri용으로 만든 식별 가능한 아이콘을 사용합니다. 참고 사진에 나온 타사 앱 아이콘은 복제하지 않습니다.
3. `deploy/macos/build-app.sh`는 임시 빌드 공간에서 두 아키텍처의 CLI와 런처를 만듭니다. CLI에는 `CGO_ENABLED=1`, 해당 `GOARCH`와 이에 맞는 clang `-arch`를 지정합니다. `lipo -create`로 각각 Universal 실행 파일을 만든 뒤 `Contents/MacOS/{kuri,kuri-launcher}`, `Contents/Info.plist`, `Contents/Resources/kuri.icns`를 조립합니다. 별도의 `codesign` 단계는 추가하지 않습니다. Apple Silicon 링커가 생성하는 실행용 ad hoc 서명은 보존합니다. [Apple의 Apple Silicon 서명 설명](https://developer.apple.com/documentation/macos-release-notes/macos-big-sur-11_0_1-universal-apps-release-notes)

## 2. 참고 사진 형태의 DMG

1. `deploy/macos/dmg-settings.py`에서 `dmgbuild`로 Finder 아이콘 보기와 위치를 기록합니다. 그림과 같은 600 x 300포인트 화면을 기준으로 앱과 Applications를 각각 가로 25%, 75% 지점에 같은 높이로 배치합니다. `deploy/macos/dmg-background.png`에는 밝은 회색 바탕과 가운데의 짙은 오른쪽 꺾쇠만 그립니다. 글자와 아이콘은 Finder가 그립니다. 왼쪽에는 `files`에 지정한 실제 `kuri.app` 디렉터리를 담습니다. 오른쪽 Applications에만 `symlinks`로 절대 경로 `/Applications`를 연결합니다. 도구 막대와 사이드바는 숨기고 기본 창 크기에서 이름이 겹치거나 잘리지 않도록 실제 화면에서 조정합니다. [dmgbuild 설정 예제](https://dmgbuild.readthedocs.io/en/stable/example/)
2. `deploy/macos/build-dmg.sh`를 저장소 루트에서 실행하면 번들을 임시 폴더에 만들고 읽기 전용 압축 형식인 `UDZO`로 `dist/kuri.dmg`를 생성합니다. `--output <파일 경로>`를 주면 해당 경로에 생성합니다. 자동 테스트는 매번 독립된 임시 디렉터리 안의 경로를 지정합니다. 최종 파일과 같은 파일시스템에서 완성된 임시 DMG를 이동해 실패한 재빌드가 이전 결과를 덮지 않도록 합니다. 작업이 끝나면 이번 빌드의 임시 파일과 마운트만 정리합니다. `.gitignore`는 생성물 경로 `/dist/`를 제외합니다.
3. DMG를 만드는 Mac에는 macOS 14 이상, Go 1.27.3, macOS Command Line Tools, Python 3.11 이상과 `dmgbuild==2.0.0`이 필요합니다. `deploy/macos/dmg-requirements.txt`에 패키징 도구 버전을 기록합니다. README에는 가상 환경에 이 도구를 준비하는 방법과 빌드 명령을 넣습니다. Finder 자동화 권한 없이 화면 배치를 기록할 수 있어 이 도구를 선택했습니다. 앱에는 Python이나 DMG 빌드 도구를 포함하지 않습니다. 사용 안내에는 실제로 앱을 실행해 확인한 macOS 버전과 아키텍처를 기록합니다. [dmgbuild 2.0.0 릴리스](https://github.com/dmgbuild/dmgbuild/releases/tag/v2.0.0), [dmgbuild 문서](https://dmgbuild.readthedocs.io/en/stable/index.html)
4. README의 시작 안내에 DMG 열기, Applications로 드래그, 디스크 이미지 꺼내기, 복사한 앱 열기를 순서대로 적습니다. 첫 실행에서 나타날 수 있는 두 상황도 설명합니다. 인터넷에서 받은 앱은 Gatekeeper가 차단할 수 있고, macOS 정책이 허용하면 사용자가 신뢰하는 앱에 한해 시스템 설정에서 열기를 승인할 수 있습니다. 앱이 열린 후 80번 포트를 등록할 때는 기존 kuri가 별도로 관리자 인증을 요청할 수 있습니다. [Apple의 앱 열기 안내](https://support.apple.com/guide/mac-help/mh40617/mac)

PATH에도 가짜 `kuri`를 둡니다. 번들의 CLI만 한 번 호출되며 인자가 정확히 `start` 하나인지 확인합니다. 테스트는 환경에 설정한 `KURI_LAUNCHD_START` 제거, 기존 PATH 보존, Homebrew 경로와 자식 종료 코드도 확인합니다. 구현 전 실패와 구현 후 통과를 기록합니다. |

| 회귀와 재실행 | `go test ./...`, `go build ./...`, 두 스크립트에 `bash -n`을 실행합니다. 같은 임시 출력 경로로 연속 두 번 DMG를 만들고 두 번째 결과도 마운트해 검사합니다. 후속 빌드가 실패했을 때 기존 DMG가 여전히 유효한지 확인합니다. Intel 하드웨어 또는 Rosetta가 있을 때만 Intel 실행 결과를 기록합니다. |

## Commit Plan

1. **`feat(macos): Finder에서 kuri start를 실행하는 앱 번들 추가`**. `cmd/kuri-launcher/main_darwin.go`와 `main_darwin_test.go`에 런처와 호출 테스트를, `deploy/macos/Info.plist`, `kuri.icns`, `build-app.sh`에 앱 조립을 추가합니다. 계획 문서를 함께 커밋합니다. 런처 테스트와 번들 검증을 마치면 이 단위를 로컬에 커밋합니다.
2. **`feat(macos): 드래그 설치용 Finder 화면을 갖춘 DMG 생성`**. `deploy/macos/dmg-settings.py`, `dmg-background.png`, `dmg-requirements.txt`, `build-dmg.sh`, `test_dmg.py`에 화면 구성과 이미지 생성 및 검증을 추가합니다. `.gitignore`와 `README.md`에 생성물 경로, 설치 및 빌드 안내를 반영합니다. 실제 검증 결과를 이 계획에 기록한 뒤 두 번째 로컬 커밋을 만듭니다. 완성된 DMG는 작업 공간에 남깁니다.

## 검증 결과

- macOS 26.6.2에서 런처 테스트가 구현 전에 실행 파일 부재로 실패하고 구현 후 통과했습니다. 번들 plist, 두 실행 파일의 권한과 Universal 아키텍처를 확인했습니다. CLI의 `help`를 Apple Silicon 네이티브와 Rosetta에서 각각 실행했습니다.
- Launch Services가 공백을 포함한 임시 앱 경로에서 런처를 실행했습니다. 기록용 CLI는 전달받은 값으로 `start` 한 개와 launchd 전용 환경 변수 제거를 기록했습니다. `go test ./...`, `go build ./...`, `bash -n deploy/macos/build-app.sh`를 통과했습니다.
- 앱과 링크만 들어 있는 시험용 DMG는 체크섬이 유효했으며 Finder 배치가 없어 구조 테스트에서 실패했습니다. 완성한 읽기 전용 `UDZO` 이미지에서는 앱 번들, Applications 링크, 두 아키텍처, Finder 아이콘 위치 및 배경을 확인했습니다.
- Finder에서 DMG를 열었을 때 왼쪽 앱, 가운데 화살표, 오른쪽 Applications가 표시됐습니다. 드래그해 `/Applications/kuri.app`에 복사하고 디스크 이미지를 꺼냈습니다. 복사한 앱을 Launch Services로 두 번 열어 `kuri is already running.`과 기존 서비스 PID를 확인했습니다. 복사 검증에 사용한 앱은 Applications에서 임시 폴더로 옮겼습니다.
- 파일 경로에 공백이 있는 위치에서 연속 빌드 두 번을 검증했습니다. DMG 도구가 실패하면 기존 결과의 SHA-256이 바뀌지 않았으며 임시 빌드 폴더가 정리됐습니다. `go test ./...`, `go build ./...`와 두 셸 스크립트의 `bash -n` 검사를 통과했습니다.
- 디스크 이미지에 배포용 서명이 없고 앱의 Apple Silicon 실행 파일에 도구 체인의 기본 ad hoc 서명만 있는 것을 확인했습니다. `syspolicy_check distribution`은 배포용 서명과 공증이 없는 앱을 거부했습니다. 격리된 macOS 환경에서의 다운로드 후 Gatekeeper 승인과, LaunchDaemon이 없는 환경의 첫 포트 등록은 미확인입니다. 현재 Mac의 기존 서비스는 실행 상태를 유지했습니다.

## 리뷰 반영 결과

- Finder에서 표준 오류가 버려지는 경로는 최근 시작 오류를 `~/Library/Logs/kuri/startup.log`에 최대 64 KiB까지 남깁니다. 기록용 CLI로 `start` 단독 실행, 0600 권한, 로그 한도, 성공 뒤 마지막 오류 유지와 Launch Services의 기본 실행 경로를 확인했습니다.
- DMG 빌드 실패 시 이번 빌드의 임시 이미지에 연결된 장치를 분리한 뒤 임시 파일을 지웁니다. `dmgbuild`가 볼륨을 마운트한 뒤 `sync`를 실패시키는 검증에서 해당 장치만 분리됐습니다. 같은 이름의 다른 볼륨과 이전 DMG는 유지됐습니다.
